## 1. 一趟完整的更新（五步）

```bash
cd app

# ① 手机上改：牌库 → 那副牌 → 导出（得到 猫卡/牌组名_日期-时间.zip）
#    改什么就改什么：图、牌面样式（调整牌面）、文案、色号 —— 一次导出全带回来。

# ② 同步回工程（先 dry-run 核对，再 --确认）
python3 tools/更新牌组.py hero <你导出的牌组包>.zip
python3 tools/更新牌组.py hero <你导出的牌组包>.zip --确认

# ③ 校验 + 生成注册表（★ 不跑生成，走查和构建都会红）
python3 tools/内置牌组.py 校验
python3 tools/内置牌组.py 生成

# ④ 验证：三套走查 + 外置资源图那支 + 门禁（只跑源码，见第 5 节）

node 走查-占卜桌选牌台.js

# ⑤ 构建交付：构建号 +1 → 打包（打包前会自动跑构建门禁，红了不出包，见 §5b）
```

手工解开包再喂给它，排查问题时方便。

## 2. 这条命令到底同步了哪四样

| # | 同步什么 | 落到哪 | 老装机看得到吗 |
|---|---|---|---|
| ① | **牌面图** | `decks/<key>/faces/` + `www/assets/deckimg/<key>/`（原字节），卡的 `image` 写成相对路径 | ✅ 自动（`restoreBuiltinImages`） |
| ② | **出厂牌面样式** | `deck.json` 的 `cardStyle`（`STYLE_KEYS` 全量） | ✅ 自动（`applyBuiltinCardStyle`） |
| ③ | **文案** | 卡的 `name / keyword / meaning / faceText / symbol / sym` | ❌ **不自动**（见 §4，要跟走得走 `retiredNames`） |
| ④ | **色号** | 卡的 `color`（导出包里是 `#rrggbb`，内置源要的是 `PALETTE` 下标） | ❌ 同 ③ |

它**不碰**牌组身份类的字段 —— `key / name / order / back / retiredNames / note / manual / addIfMissing / seed`。
那些是"这副牌是谁"的问题，改动走 00 或手改。

**对齐按卡名，不按顺序**：所以导出包里卡序乱一点没关系。
但**多了卡 / 少了卡一律报警**、交给人工 —— 本工具不加卡、不删卡（那是 00 §1 / §11 的事）。

## 3. 图片：一律外置，且绝不重编码

规矩和 00 §12 是同一条（那边讲"插画牌组为什么不能内嵌"，这边只管"怎么落"）：

| 环节 | 是什么 |
|---|---|
| 工程内**真源** | `decks/<key>/faces/<n>.<ext>`（不进包） |
| 进包资源 | `www/assets/deckimg/<key>/<n>.<ext>`（`shutil.copy2` 原字节进，零重编码） |
| 卡的 `image` | `assets/deckimg/<key>/<n>.<ext>`（**相对路径**，不是 data URL） |

- **命名**：按注册表里的卡序自动编号（`01.jpg`、`02.jpg`…）。
- **几卡共用一张图**：按**内容**去重 —— 同一张只落**一份**文件，那几张卡的 `image` 写**同一条路径**。
  （2026-10-12 Overflow：16 张共用一张 1080×1620 的图，进包只占 0.25 MB；
  要是按 16 份落，就是 4 MB 的纯重复。）
- **换图 = 覆盖**：`faces/` 里本轮没用到的旧图会被清掉（工具会打印"清掉不再用的旧图"）。
- **牌背不归本流程**：牌背是 `decks/<key>/back.svg`（矢量模板）或 `library.js` 的 `BACK_TPL`。
  导出包里的 `backImagePath` 非空时工具只会**提示**一句，不替你动 —— 要换牌背照 00 §12 第 3 条做。
- **牌背已经接成外置图的**（hero / overflow 都是）：`back.svg` 里就一条
  `<image href="assets/deckimg/<key>/_back.jpg">`，换图＝把新图**原字节**盖到**这两处**
  （`decks/<key>/faces/_back.jpg` 真源 ＋ `www/assets/deckimg/<key>/_back.jpg` 进包），
  `back.svg` / `deck.json` / 注册表**都不用动**（2026-10-17 构建 259 就是这么做的）。
  本工具只**提示**，不会替你搬这张图 —— 提示里会写清是哪一个文件。
  > ⚠ 2026-10-17 前这里有个雷：`--确认` 的"保留集"只认卡面图，`_back.jpg` 会被当旧图
  > **连源图一起删掉**。现在 ④ 把 `back.svg` 引用的文件名也并进保留集，`--检查` 还会盯它真在不在
  > （缺了当场红：`牌背引用的图不在磁盘上`）。加新守卫的测试法：造个假旧图 + 故意写错一张卡的
  > `image` 逼出清理分支，看假图被清而 `_back.jpg` 还在。

> ⚠ **注册表体积是这条流程的体温计**：`ls -la www/js/builtin-decks.js`。
> 超过 **3 MB** 就是又开始内嵌 base64 了（2026-10-12 英雄之旅换外置后：1.27 MB → 229 KB）。

## 4. 老装机上会怎样（三条链，只有两条自动）

内置牌组是"装机时建一次"的，所以"改了内容老装机怎么看得到"要靠迁移链。**三条链的脾气不一样**：

| 内容 | 链 | 判据 | 用户改过的那张卡 |
|---|---|---|---|
| **样式** | `data.js: applyBuiltinCardStyle` | 卡上的 `fxStamp` / `fx` 快照 / 历史 `cardStylePrev` 对得上 | 一根手指都不碰 |
| **图** | `data.js: restoreBuiltinImages` | `builtinImgHash` 对得上（旧卡退回 `builtinHash`） | 一根手指都不碰 |
| **文案** | `data.js: syncBuiltinCards`（00 §11） | **只按卡名"补齐缺失的卡"，不覆盖已有的卡** | 不碰 |

⇒ **改了牌义 / 牌面句，老装机是看不到的**（同名卡存在就跳过）。
要让文案跟着走，只有 00 §11 那条路：把旧卡名写进 `retiredNames`（下次开机删掉旧卡、再把新卡补回来）——
**代价是那张卡上的用户编辑一起没了**，所以这是个要用户点头的动作，别自作主张。

> 2026-10-12 用户的原话可以当结论用：「**不用管，老用户们已经学会清理数据让软件回到最初的状态了**」——
> 所以默认**不为老装机**加 `retiredNames`；真需要时再问。

## 5b. 构建门禁（打包前自动跑，红了不出包）

`build_catcard.py` 的 `[0/6]` 会调 `tools/门禁.py`，它守三条：

| # | 守什么 | 红了说明 |
|---|---|---|
| ① | **注册表一致**：`decks/*.json` ↔ `www/js/builtin-decks.js` | 改了 JSON 忘了跑「生成」 |
| ② | **构建号 / 版本名一致**：全工程的同步点都等于 `build_catcard.py` 的 `CODE` / `VER`，且 HTML 里没有写死的版本号 | 漏改一处同步点（工具会把每一处逐条列出来，对不上的标红） |
| ③ | **专属补丁都登记了**：每副进包牌组都在 `tools/内置牌组.py` 的 `DECK_PATCHES` 里 | 加牌组时忘了登记（规则见 00 §0c） |

单跑：`python3 app/tools/门禁.py`（改完随手跑一次，比等构建快）。

> **别再数"几处"了。** 构建号是"装的是哪一次"的唯一指纹，历史上真漏过；
> 项目记录 §1 原来那句「构建号是**四处**手改的」就是**手抄**（项目自己的规矩：手抄的必然过期，见 00 §0c），
> 2026-10-12 被用户当场抓过期 —— `index.html` 抽屉底部还躺着 `猫卡 2.1.0 · 239`，而构建号早滚到 241。
> 现在**权威出处只有** `build_catcard.py` 的 `CODE` / `VER`，其余同步点由 `tools/查构建号.py`
> 扫全工程数出来比对（当前 **9 处**：构建号 5 + 版本名 4），多一处少一处、写错一处，机器都认得。
>
> ★ **铁律（要显示版本号的新地方）**：一律读 `MoKa.settings.VERSION / BUILD`，
> **绝不在 HTML 里写死字符串**（`app.js` 灌 `#drawer-ver` 就是范例）。
> 走查-壳层与丢图.js 第 2 组专门盯着 `index.html`：写死了就红。

## 6. 常见红灯

| 现象 | 意思 / 怎么办 |
|---|---|
| `张数对不上`（旧的图工具） | 图数和卡数不等 —— 要么补齐/删掉多余的图，要么这张图就是"全副共用"（见 §3） |
| 工具报 `样式**不统一**` | 导出包里各卡样式不一致（用户在手机上逐张调过）→ 别硬写 `cardStyle`，得人工决定写哪版 |
| 工具报 `色 X 不在调色板里` | 用户用了调色板以外的自定义色 → 内置源只存 `PALETTE` 下标，要么把它加进 `data.js` 的 `PALETTE`，要么接受丢这个色 |
| 工具报 `导出包里没有的卡` / `有内置源没有的卡` | 加卡/删卡不走这条流程（00 §1 / §11） |
| 注册表 > 3 MB | 图又被内嵌了 —— 检查 `image` 是不是 data URL |
| 走查第 6 组红一片 | 换了图片范式没同步断言（见 §5） |
| 构建前 `生成 --检查` 红 | 忘了跑 `python3 tools/内置牌组.py 生成` |
| 门禁 ② 红：某某处构建号 ≠ CODE | 构建号没同步全（工具会指出文件:行号）—— 别手抄"几处"，照它的清单改 |
| 门禁 ③ 红：`没登记专属补丁：xxx` | 新加的牌组没在 `工具/内置牌组.py` 的 `DECK_PATCHES` 登记（真没有就写空列表，见 00 §0c） |
| 工具报 `牌背引用的图不在磁盘上` | `back.svg` 引用着的 `_back.*` 被删了（2026-10-17 前它会被"清理旧图"吃掉）—— 从 `decks/<key>/faces/` 原字节补回 `www/assets/deckimg/<key>/` |

## 7. 这套流程自己的守卫

- **工具**：`app/tools/更新牌组.py`（`--检查` 模式给构建前 / 接手时用：只比对，不写一个字）。
  它从 `data.js` **现读** `STYLE_KEYS` 与 `PALETTE` —— 手抄一份必然过期（项目的老规矩）。
- **保留集**：`--确认` 清旧图时留的是「zip 带的 ＋ 随包外置的 ＋ 卡引用着的 ＋ **`back.svg` 引用着的**」。
  第四条是 2026-10-17 补的 —— 牌背图 `_back.jpg` 不占前三条，曾会被连源图一起删掉（hero / overflow 都在雷区）；
  `--检查` 也会对 `back.svg` 引用的资源查"文件真在不在"，缺了当场红。
- **样式比较**：导出包里值为 `null` 的样式字段（`faceBg / nameColor / kwColor`）进 plan 时就剔掉 ——
  内置源历来是"省略不写"，两条路径得同一语义，否则 `--检查` 会误红（2026-10-17 修的）。
- **走查**：`走查-内置牌组.js` 第 2 组（`decks/*.json` ↔ 注册表逐字节一致，含 `image`）、
  第 6 组（外置图：注册表里是路径 / 文件真在 / 落盘原样 / 开机补回 / 用户换过的不碰）；
  另有通用的"外置资源型路径必须真实存在"守卫（对**所有**内置牌组生效）。
- **验证件**：`test/验证-外置资源图.js <key>` —— 端到端盯住注册表→磁盘→渲染→落盘→导出/导入五环。
  它**不写死张数、不认哪副牌**（雷诺曼那副的遗留已在 2026-10-12 清掉）。

## 8. 和 00 的分工（一页说明，别再合并）

| | 00 增删流程 | 01 更新流程（这份） |
|---|---|---|
| 什么时候用 | 牌组的**有无**变了 | 牌组的**内容**变了 |
| 典型动作 | `新增 / 下架 / 上架 / 删除` | 换图、换出厂样式、改文案、改色号 |
| 工具 | `tools/内置牌组.py` | `tools/更新牌组.py` |
| 真源 | `decks/<key>/deck.json`（同一份） | 同左 |
| 收尾 | 校验 → 生成 → 走查 → 构建 | 同左 |

**为什么不合成一份**：两条链的**风险面**完全不同 ——
增删动的是"注册表里有没有这一条"（会牵动代码里的硬引用、专属模板、`不打包.txt`，
删错不可逆）；更新动的是"这一条里的内容"（错了看得见、改了能再改一遍）。
一份文档同时讲两件事，最容易被"照着上半段做了、漏了下半段"。
